# Часть 4. Мониторинг: Prometheus и Grafana


Добавляю наблюдение за системой: собираем метрики и показываем их
на графиках. Смотрим два уровня: **приложение** (сколько запросов, какая скорость)
и **сервер** (процессор, память, диск).

## Из чего состоит система

| Компонент | Роль  | Где живёт |
|---|---|---|
| `/metrics` в приложении | Приложение само отдаёт свои «показатели приборов» в понятном Prometheus формате | внутри приложения (шаг 1) |
| Prometheus | Сборщик: раз в 15 секунд опрашивает все источники метрик и сохраняет значения во временную базу | контейнер на сервере мониторинга, порт 9090 |
| node-exporter | Программа, которая отдаёт метрики самого сервера (CPU, RAM, диск) | контейнер рядом, порт 9100 |
| Grafana | Визуализация: дашборды, графики, таблицы | контейнер, порт 3000 (логин admin/admin) |

## Схема

```
                 ┌─────── сервер мониторинга (EC2) ───────┐
                 │                                        │
   Prometheus ───┼── каждые 15 секунд ──► node-exporter   │  (метрики сервера)
     :9090       │                  └──► nginx :80        │  (метрики приложения,
                 │                        │               │   nginx проксирует
                 │  Grafana :3000 ◄───────┘               │   на поды в кластере)
                 └────────────────────────────────────────┘
```


Prometheus обращается по адресу сервера мониторинга `:80` — туда слушает nginx,
а nginx уже сам балансирует запрос между подами приложения в Kubernetes. Плюс:
если поды переехали на другие машины, настройки Prometheus менять не нужно —
достаточно обновить nginx.

**Почему весь стек живёт вне Kubernetes?** Если кластер упадёт, мониторинг
продолжит работать и покажет это. Плюс сервер мониторинга настраивается
Ansible (шаг 3), у которого есть конкретная роль в проекте.

## Как это работает

1. Приложение при каждом запросе увеличивает счётчики (`http_requests_total`)
   и замеряет время ответа (`http_request_duration_seconds`) — см. шаг 1.
2. Prometheus по расписанию скачивает страницу `/metrics` через nginx.
3. Проверки здоровья (`/healthz`, `/readyz`) в метрики **не попадают** —
   специально, чтобы цифры отражали только реальные запросы пользователей.
4. Grafana читает базу Prometheus и рисует дашборды. Готовый дашборд сервера —
   импорт по номеру **1860** (Node Exporter Full).

## Где увидеть

- Открыть `http://<IP_сервера>:9090/targets` — оба источника в статусе UP (зелёные).
- На вкладке Graph запросить `http_requests_total` — график растёт при
  обращениях к приложению.
- Открыть `http://<IP_сервера>:3000` — дашборды Grafana.

## Зависимости этапа

- **Вход**: приложение с `/metrics` (шаг 1), сервер мониторинга из шаг 3,
  работающий nginx (маршрут до приложения появится в шаг 5).
- **Выход**: веб-интерфейсы Prometheus и Grafana — материал для демонстрации.
- Метрики приложения «оживают» только когда приложение задеплоено в кластер
  (шаг 2 + 5).
